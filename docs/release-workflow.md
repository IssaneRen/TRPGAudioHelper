# 两到三人协作与生产发布

主站默认分支是 `master`，Gateway 默认分支是 `main`。两个仓库都是公开仓库。2026-11-19 查询 GitHub，两个默认分支都未开启保护。本文记录建议的生产流程，供部署改造和演练使用。

## 先读这些词

| 术语 | 在这个仓库里的意思 |
| --- | --- |
| 分支、PR | 分支是一次改动的独立工作线。PR 是把这条工作线合入默认分支前的审查申请。 |
| worktree | 给同一个仓库另开一个本地工作目录。两项任务可以各在自己的目录改文件。 |
| CI、runner | CI 是提交后的自动检查，例如运行测试和构建。runner 是实际执行检查的机器或环境。 |
| SHA、SHA-256 | 发布清单里的代码 SHA 指定某次 Git 提交。归档的 SHA-256 则是压缩包的校验值，用来验证包是否完整。 |
| squash merge | 将一个 PR 的多条开发提交合成一条，再放进默认分支的历史。 |
| current、flock | `current` 是服务器指向当前代码版本的软链接。`flock` 是发布脚本用的文件锁，使同一时间只有一个脚本可以切换线上版本。 |
| 健康检查、回滚 | 健康检查验证新版本能提供服务。回滚把运行中的代码切回已验证的版本。资料恢复另按备份流程操作。 |

## Git 与代码审查

- 每项任务从对应默认分支开短分支。一个人同时处理多项任务时，每项任务用独立 `git worktree`。同一接口、迁移或生成文件由这一项任务的负责人维护。共同改接口前先对齐请求、响应及兼容方式。
- 把默认分支设为受保护分支，要求 PR、至少一人审阅、处理完审阅意见、分支与目标分支同步并通过必需检查。使用 squash merge，每个合并提交保留对应 PR。禁止默认分支直接推送、强推和删除。两三个人可以用 GitHub 的严格状态检查，有频繁等待时再考虑合并队列。
- 主站 PR 检查 `pnpm install --frozen-lockfile`、类型与生产构建。Gateway PR 检查锁文件、服务测试和构建。稳定命名的必需检查覆盖每个 PR。PR 开发使用合成数据和临时目录，生产凭据仅供发布任务使用。
- 跨仓需求互链两个 PR，通过一组 API 契约和部署清单串起来。默认先发兼容旧前端的 Gateway，再发前端。涉及删除字段时先停止旧消费者，用后续发布做清理。两仓 SHA 因此都能单独追溯。

[GitHub 分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 现有发布冲突

主站 `deploy.yml` 对 `master` 所有推送生效。Wiki 或博客提交可同时触发 `deploy-content.yml`，它直接向 `current` 解包。UI 变更可同时触发 `deploy-static-overlay.yml`，它复制当前版本再切换相同的 `current`。本地 `scripts/deploy-direct.sh` 也切换这个指针。Gateway 的上传使用固定的 `/tmp/trpg-ai-gateway.tar.gz`，后到的上传可能覆盖先到的包。这些入口缺少主机级协调，上线顺序可能与合并顺序不同。

## 收敛成一条生产发布链路

1. 每仓保留一条构建链路。合并后按 SHA 执行冻结安装、测试、打包，输出归档、SHA-256 和构建清单。清单记录代码 SHA、运行时版本及兼容要求。归档包含发布所需代码和静态文件。
2. 由一个生产工作流晋升已通过 CI 的归档。跨仓发布选定两个 SHA，使用同一张发布清单。仅生产发布作业持有最小权限的 SSH 凭据。公网 PR 使用 GitHub 托管 runner 和只读仓库权限。
3. GitHub `concurrency` 串行化生产作业，已经开始的切换持续到完成。服务器上再用同一个 `flock` 锁覆盖前端、Gateway、运维发布和回滚。从校验归档、检查上一个已发布版本、备份、切换到冒烟检查都在锁内。跨仓和手动入口走同一个部署脚本。默认晋升拒绝旧于当前版本的构建，回滚走显式命令。
4. 使用 `<SHA>-<run_id>-<run_attempt>` 作为上传目录。校验后解包到同一文件系统的临时目录，检查清单和入口文件，再提交为只读版本目录。每次切换用临时软链接加原子重命名。运行时 Wiki 和博客由原有独立内容目录提供，归档解包只写新版本目录。静态覆盖旧入口在新链路演练通过后退出生产。
5. 发布前运行 `nginx -t` 和必要的运行时检查。Gateway 切换后从本机检查 `/health`，再检查前端静态资源和公开只读接口。失败时恢复上一版本指针和必要的服务配置，重启后复验。保留最近几个已知可用归档及当前、上一版指针。

工作流并发组只在单仓生效。GitHub 默认至多保留一个等待中的任务，发布直接选定归档时可按团队需要使用 `queue: max`。服务器锁仍是跨仓入口的共同约束。

[GitHub Actions 并发控制](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)

## 保护数据与验证恢复

- 持久数据放 `shared/` 或现有独立运行时目录，文件由服务账户读写。发布包和 PR 排除世界观原稿、SQLite、作品草稿、密钥和真实测试数据。
- 常规发布沿用稳定数据目录。迁移发布提前生成一致性备份并记录快照 ID。每个世界观使用 SQLite 在线备份，连同目录 SQLite、现有 Wiki、上传项和工作台数据分别纳入备份计划。定期加密传到另一处，校验完整性并在临时目录试恢复。工作台加密文件还需要独立保管其密钥恢复材料。
- 数据库升级先扩后缩，事务内写入 schema 版本。代码回滚优先使用兼容旧版本的数据结构。恢复快照前保存当前状态并评估备份之后的写入，快照恢复走单独的运维操作。两个维护者同时保存同一篇文章时，用修订号返回冲突，浏览器保留本地修改供合并。
- 第一轮演练使用隔离目录和合成数据。并行提交两份归档验证锁，模拟旧任务迟到、归档哈希错误和健康检查失败，验证保留上一个可用版本，并从备份还原一份世界观数据。

[SQLite 在线备份](https://www.sqlite.org/backup.html)

## 维护日志

PR 使用「功能」「修复」「运维」「兼容性」标签，并写一句用户可见更新。GitHub Release 按标签汇总 PR，发布前补兼容要求、迁移影响与操作说明。按实际生产成功上线的版本发布更新日志。

服务器维护追加式发布流水，建议保存在 `/var/lib/trpg-deploy/releases.jsonl`，并保存到异机。每次记录 UTC 时间、环境、发起人或 Actions Run、网站与 Gateway SHA、归档校验值、上一个版本、迁移或备份编号、健康检查和上线结果。回滚记一条新事件。日志只记录操作元数据。GitHub Release 回答「变了什么」，发布流水回答「哪一版真正上线了」。

[GitHub 自动生成发布说明](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes)
